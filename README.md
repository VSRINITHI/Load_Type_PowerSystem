# Power-System Load-Type Classification

A reproducible machine-learning workflow for classifying industrial electricity readings into **Light**, **Medium**, and **Maximum** load types. The project uses chronological validation, feature engineering, model comparison, error analysis, and a reusable inference pipeline.


## Project structure

```text
Load_Type_Classification/
├── Load_Type_Classification.ipynb   # Final, documented end-to-end workflow
├── load_type_pipeline.py            # Reusable preprocessing, features, baseline and inference
├── load_data.csv                    # Source dataset
├── requirements.txt                 # Python dependencies
├── README.md                        # Project and version-history documentation
└── outputs/                          # Generated by the notebook (model bundle and reports)
```

The notebook contains a `%%writefile` cell that can regenerate `load_type_pipeline.py`. The standalone module is included deliberately so a saved model bundle can be loaded and used from a separate Python process without depending on notebook execution.

## Problem and approach

- **Target:** `Load_Type` — Light, Medium, or Maximum.
- **Data frequency:** 15-minute readings.
- **Recorded dataset size:** 35,040 cleaned rows; 32,064 rows from January–November 2018 and 2,976 December 2018 rows in the saved notebook outputs.
- **Feature families:** calendar/time-of-use, electrical measurements, and causal temporal features derived from current and past readings.
- **Models compared:** a most-frequent dummy baseline, a rule baseline, Logistic Regression, Decision Tree, Random Forest, HistGradientBoosting, and a tuned HistGradientBoosting candidate.
- **Primary metric:** macro-F1, so performance across the three classes is not dominated by the largest class.

The workflow also includes data-quality checks, class-wise evaluation, post-hoc December diagnostics, permutation importance, feature-group ablation, model-bundle creation, and inference checks.

## Validation and leakage controls in v4

1. **Chronological forward CV:** each validation month follows the training months; the notebook uses July–November validation folds.
2. **Fold-specific preprocessing:** clipping/winsorisation caps are calculated from each fold's training rows rather than using future validation data to prepare the fold's features.
3. **Training-only learned transforms:** imputation and model fitting are fitted on the relevant training data.
4. **Leakage regression check:** future data is deliberately modified and the notebook checks that the earlier fold's training features remain unchanged.
5. **Feature ablation:** calendar-only, calendar + electrical, and full temporal feature sets are compared using forward CV; December results are kept as post-hoc diagnostics.
6. **Champion selection:** the final candidate is selected using forward-CV macro-F1 and a declared simplicity preference, rather than choosing the model after inspecting December performance.

## Run the project

1. Keep `Load_Type_Classification.ipynb`, `load_type_pipeline.py`, and `load_data.csv` in the same project directory.
2. Start Jupyter Notebook or JupyterLab.
3. Open `Load_Type_Classification.ipynb`.
4. Choose **Restart Kernel and Run All Cells**.
5. Confirm every cell completes, the leakage check passes, and the model-selection and inference checks finish successfully.
6. Inspect the generated `outputs/` artifacts, including the saved model bundle and metrics/report files.

The notebook writes the pipeline module early in execution. Keeping the standalone `.py` file in the repository is still recommended for direct inference and to make the project layout clear.

## Using the saved inference pipeline

After running the notebook and confirming that `outputs/load_type_model.joblib` was created, the module exposes the bundle-loading and raw-input prediction utilities. A typical usage pattern is:

```python
import load_type_pipeline as pipeline

bundle = pipeline.load_bundle("outputs/load_type_model.joblib")
predictions = pipeline.predict_from_raw(raw_dataframe, bundle)
```

Use the exact input schema expected by `load_type_pipeline.py`; inspect its `RENAME`, cleaning, and validation definitions before integrating with another data source. The example assumes `raw_dataframe` contains the required source columns and is intentionally not a standalone runnable example without that input data.
